# 배치 실행·복구 정합성 감사

2026-09-05. 실제 GPU 생성 없이 loopback HTTP/WebSocket 서버, 임시 sql.js DB와 출력 폴더로 검증했다.

## 실패 주입과 수정 결과

| 주입 위치                                           | 수정 전 재현                                       | 수정 후                                                                         |
| --------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------- |
| `/prompt` 수락 직후 응답 소켓 종료                  | 동일 태스크를 두 번 제출                           | 한 번 제출 후 `uncertain`, 작업 일시정지 및 자동 재개 차단                      |
| POST 응답 전에 WS 완료 이벤트 전달                  | 이벤트를 놓쳐 실패                                 | 최초 REST 조회로 완료 확인                                                      |
| WS 단절·중복·다른 요청의 지연 이벤트                | 이벤트 의존과 단절 시 대기 시간 재설정 위험        | 요청 ID 필터·단일 deadline·중복 조회 병합, 완료된 history만 승인                |
| 두 번째 이미지 GET 실패                             | 첫 파일 정리 후 원격 생성까지 다시 실행            | 같은 prompt의 다운로드만 재시도; gallery·부분 파일 없이 실패, 서버 history 유지 |
| 파일 쓰기 중 예외                                   | 저장 경로 등록 전에 생긴 부분 파일 잔존            | 배타적 생성 직후 정리 대상 등록, 실패 시 해당 시도의 파일 정리                  |
| 이미지 GET 응답을 보류하고 취소 후 해제             | 취소 뒤 gallery와 완료 상태 기록                   | 커밋 직전 취소 확인, 미커밋 파일 정리; 전역 interrupt 전송 없음                 |
| paused 작업의 running 태스크를 DB에 저장하고 재시작 | 복구에서 누락되어 실행 중 태스크를 둔 채 작업 완료 | 요청 ID를 보존하고 같은 서버 결과로 복구                                        |
| DB 스냅샷 rename 실패                               | `flushDatabase()`가 성공 반환                      | 요청한 revision 저장 실패를 호출자에게 전달                                     |
| 서버의 명시적 실행 실패 후 재시도                   | 리팩터링 중 DB 재시도 횟수 이중 증가 발견          | 실제 추가 시도당 한 번 증가하는 회귀 테스트 적용                                |

일시정지 중 현재 태스크는 결과 기록까지 진행할 수 있으나 다음 태스크 제출은 재개까지 대기한다.
서버가 실행을 명시적으로 실패했다고 확인한 경우에만 새 제출로 재시도한다. 결과 저장 실패는
기존 요청 ID를 유지한다. 생성할 태스크는 기존 행을 먼저 사용하고 최대 `sort_order` 다음부터
확장하여 미완료 행과 랜덤 시드를 재생성하지 않는다.

## 실제 프로세스 종료

`output-crash.test.ts`는 production 파일 저장·journal·DB 코드를 자식 프로세스에 번들하고
정상 종료나 `closeDatabase()` 없이 `process.exit()`한다. 부모가 DB를 다시 열어 검사한다.

| 종료 시점                | 재시작 시 관찰                                      |
| ------------------------ | --------------------------------------------------- |
| 첫 이미지 저장 후        | 파일 1개, gallery 0, 미해결 journal 보존            |
| 모든 이미지 저장 후      | 파일 2개, gallery 0, 미해결 journal 보존            |
| DB 트랜잭션 후 flush 전  | 메모리 완료 상태 소실, 파일과 journal 보존          |
| flush 후 journal 삭제 전 | DB 완료·gallery 2개 유지, 파일 보존, journal만 정리 |

파일과 DB는 하나의 트랜잭션으로 커밋할 수 없다. journal에 파일 생성 의도를 먼저 기록하고,
불일치를 발견하면 자동 생성을 멈춰 증거를 보존한다. 미해결 journal의 경로만 믿고 파일을
삭제하지 않는다. 시작 시 완료된 태스크와 DB 등록·파일 존재를 확인한 journal만 제거한다.

## 남은 제약

- ComfyUI와 앱 사이에 분산 트랜잭션이나 확인된 멱등 제출 계약이 없다. 수락 응답을 잃었거나
  서버가 history를 잃으면 실행 여부를 확정할 수 없으며 exactly-once를 보장하지 않는다.
- 미확정 상태의 수동 대조·해결 UI는 아직 없다. 파일과 journal, 요청 ID를 보존하며 자동 재개와
  증거를 지우는 삭제·재실행을 막는다. 복제는 명시적인 새 생성으로 중복 가능성이 있다.
- 손상된 journal처럼 태스크를 특정할 수 없는 복구 실패는 전체 시작을 차단한다. 이 경우
  태스크별 경고 대신 시작·재개 오류와 로그로 원인을 확인한다.
- 취소는 로컬 처리를 중단한다. 다른 클라이언트의 작업에 영향을 줄 수 있는 전역 interrupt를
  보내지 않으므로 이미 수락된 원격 작업은 계속 실행될 수 있다.
- 테스트는 프로세스 종료를 다룬다. 전원 손실·장치 고장·파일시스템의 디렉터리 동기화 보장,
  외부 프로그램의 DB/이미지 변경, 모든 ComfyUI 커스텀 노드의 동작을 보증하지 않는다.
- crash worker의 HTTP 다운로드는 Windows native fetch 종료 문제를 피하기 위해 `node:http`를
  사용한다. production REST/WS 클라이언트는 별도의 실제 HTTP/WS 테스트에서 검증한다.
- 새 상태가 기록된 DB를 이전 앱 버전으로 다시 여는 동작은 지원을 검증하지 않았다.

관련 회귀는 `queue-faults`, `wait-for-prompt`, `task-output`, `output-journal`, `output-crash`,
ComfyUI `fault-server`, DB `index`·`repositories`, IPC `handlers` 및 renderer 작업 컴포넌트 테스트에 있다.

검증: 전체 56개 파일·595개 테스트와 coverage 게이트, ESLint, main/renderer 타입 검사 및
Electron production 빌드 통과. 배치 서비스 라인 커버리지는 93% 수준이다.
