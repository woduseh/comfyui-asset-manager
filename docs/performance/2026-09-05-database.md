# DB 저장과 배치 프롬프트 정리 성능 실측

2026-09-05에 실제 DB 서비스와 sql.js, 임시 파일 저장을 사용해 두 병목을 재현하고 수정했다.
5만 건 규모에서 저장 중앙값은 **93.63 → 77.58ms**, 완료 프롬프트 정리는
**17.85 → 0.39ms**로 줄었다. 데이터, 저장 순서, fsync, 오류 전달과 복구 계약은 유지한다.

## 조사와 선정 근거

앱의 주요 경로는 배치 구성 → ComfyUI 실행 → 결과 저장 → 갤러리 선별이다.
기존 테스트·Vitest 설정과 DB·큐·IPC·renderer 호출 경로를 조사했다. 기존 성능 벤치마크는
없어서 해당 DB 경로만 실행하는 측정 스크립트를 추가했다.

| 후보                                           | 확인한 근거                                                                                                                                                                                                       | 판단                                                         |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 저장 시 전체 DB 추가 복사                      | `ensureSaveLoop()`와 동기 writer가 `Buffer.from(db.export())`를 호출. 큐는 제출 전·요청 ID 수신 후·완료 기록 후 `flushDatabase()`를 기다린다. 5만 건 fixture에서 호출당 116,469,760바이트의 추가 복사를 관측했다. | 반복되는 저장 지연과 할당 비용을 줄이고 변경이 작아서 구현   |
| 완료 프롬프트 반복 갱신                        | 큐는 50개 태스크 청크 5개마다 정리한다. 기존 쿼리는 이미 `'{}'`인 행까지 포함해 5만 행을 갱신했다. `getRowsModified()`와 실제 SQL의 실행 계획으로 확인했다.                                                       | 250개 새 완료만 정리하도록 구현                              |
| 작업 목록의 snapshot 전달·최근 결과 COUNT      | BATCH_LIST가 큰 snapshot까지 전달하고 Jobs의 최근 결과 조회가 사용하지 않는 COUNT도 계산한다. 호출 구조만 확인했다.                                                                                               | 응답 데이터 범위·IPC 계약 변경은 이번 범위에서 보류          |
| 큰 모듈 선택·작업 이력 DOM, 원본 이미지 decode | 숨겨진 단계의 checkbox 생성, 전체 이력 렌더링, thumbnail 부재 시 원본 사용을 확인했다. 실제 렌더링 비용은 미측정이다.                                                                                             | 실제 Electron 프로파일과 선택·탐색 동작 검증이 필요해서 보류 |

갤러리와 queue store의 요청 합치기, 선택 아이템만 저장하는 스냅샷, 지연 조합 생성은 이미
있거나 사용자가 수정 중인 코드다. 이번 개선 실적으로 계산하지 않았다. 새 캐시·동시성·의존성은
추가하지 않았다.

## 구현

- [DB writer와 스키마](../../src/main/services/database/index.ts): sql.js가 반환한 독립적인
  `Uint8Array`를 파일 API에 직접 전달한다. async/sync 두 경로의 추가 `Buffer` 복사를 제거했다.
  `write → sync → close → rename`, 직렬 writer, 재시도·종료 처리 순서는 그대로다.
- [태스크 repository](../../src/main/services/database/repositories/index.ts): 정리 조건에
  `prompt_data != '{}'`를 추가했다. `completed` 상태와 대상 job 조건은 유지한다.
- DB 초기화에서 `(job_id, status)`의 부분 인덱스 `idx_batch_tasks_prompt_cleanup`을 생성한다.
  인덱스 조건도 `status = 'completed' AND prompt_data != '{}'`다. 이미 정리한 이력이 아니라
  남은 정리 대상을 조회하며, 기존 DB에도 자동 생성한다.
- [회귀 테스트](../../tests/main/services/database/performance-contracts.test.ts),
  [측정 실행기](../../scripts/benchmark-database.mjs),
  [측정 시나리오](../../scripts/performance/database-worker.mjs)를 추가했다.

sql.js 1.14.1의 로컬 구현에서 `Database.export()`는 `FS.readFile()`이 새로 할당한
`Uint8Array`를 반환한다. 이 소유권을 확인하고 쓰기 대기 중 DB 변경 테스트로 검증했다.
원본 DB를 비동기 쓰기 중 공유하는 방식으로 바꾸지 않았다.

## 측정 조건

- Windows 10.0.26200, AMD Ryzen 7 7800X3D, 논리 CPU 16개, RAM 약 31.2GiB.
- Node.js 24.14.0 (`.node-version` 일치), sql.js 1.14.1. 실제 Electron 프로세스가 아닌 Node에서
  production DB/repository 코드를 번들링했다. Electron의 userData 위치와 logger만 대체했다.
- 규모별로 완료 태스크 N개와 생성 이미지 메타데이터 N개를 구성했다(N=5,000 / 50,000).
  이미지에는 동일 길이의 프롬프트·negative·생성 파라미터를 넣었다. 다른 상태·다른 작업의
  보존 확인용 태스크 7개를 추가했다. 실제 이미지 파일이나 개인 DB를 읽지 않았다.
- 프롬프트 정리는 N개 중 250개에만 프롬프트를 복원한 뒤 호출했다. 복원·fixture 생성·해시
  검사는 측정 시간에서 제외했다. 정리 후 태스크와 이미지의 모든 컬럼을 정렬해 SHA-256을 비교했다.
- 저장은 실제 임시 파일 쓰기·fsync·rename을 포함한다. 호출 시작부터 최초 비동기 대기까지의
  동기 처리 시간도 따로 기록했다.
- 시나리오별 최초 1회를 별도 기록하고, 추가 5회 워밍업 후 15회 측정했다. 각 반복 직전에
  명시적 GC를 실행했다. 따라서 장시간 앱의 자연스러운 GC 동작을 재현하는 측정은 아니다.
- 5만 건은 새 프로세스에서 **변경 전 → 후 → 후 → 전(ABBA)** 순서로 실행해 버전당 30회,
  5천 건은 버전당 15회 측정했다. 표는 전체 측정값의 중앙값과 최소~최대다. 이상치는 제거하지 않았다.
- DB와 OS 파일 캐시가 준비된 상태다. 최초 호출도 fixture 생성·저장 뒤이므로 cold start로
  해석하지 않는다. OS 캐시를 비우는 실험은 하지 않았다.
- 원본은 작업 시작 시점의 사용자 변경을 포함하며, 별도 복사본의 소스 해시가 최초 측정 때와
  같음을 확인했다. 변경 전후 모두 최종 측정 스크립트와 같은 패키지·데이터를 사용했다.

5만 건 DB 크기는 116,469,760 → 116,473,856바이트였다. 차이는 초기 부분 인덱스의 4KiB다.
태스크·이미지 데이터 해시는 네 실행 모두
`53e7c7b127e419962f361f64ccf88a96b9c64c6bf28d67ca448dd43ab4672c64`로 같았다.

## 실험과 한계

아래 중간 실험은 워밍업 3회 뒤 9회씩 측정했다. 최종 결과 표는 검증 단계까지 동일한
측정 스크립트로 다시 실행한 워밍업 5회·15회 측정값을 사용한다.

1. 조건만 추가한 실험은 정리 중앙값을 19.011 → 6.237ms로 줄였지만 실행 계획은 기존
   `idx_batch_tasks_job_status`로 완료 이력 전체를 검사했다. 이를 최종 해법으로 삼지 않았다.
2. 처음 만든 `job_id` 단일 컬럼 부분 인덱스는 SQLite가 선택하지 않아 약 6.534ms로 효과가
   없었다. 해당 정의를 교체했다. 최종 `(job_id, status)` 부분 인덱스가 선택되는 것을 실제
   repository SQL의 `EXPLAIN QUERY PLAN`과 테스트로 확인했다.
3. 초기 단발 측정에서는 갤러리가 1.382 → 2.153ms로 느려져 비교 방법을 점검했다.
   최종 스크립트로 맞춘 ABBA 측정에서는 1.319 → 1.316ms였다. 초기 값을 숨기거나 모든
   환경에서 회귀가 없다고 일반화하지 않는다.
4. `copiedSnapshotBytes`는 실제 export 배열에서 새 Buffer로 복제된 바이트를 계측한 값이다.
   **프로세스 최대 RSS 감소량이 아니다.** 순간 RSS/ArrayBuffer 차이는 GC와 재사용 영향으로
   음수·0 또는 큰 변동이 있어 개선 지표로 채택하지 않았다. CPU 계측값도 원자료에만 남겼다.
5. 미정리 완료 태스크가 많은 legacy DB는 부분 인덱스도 더 커지고 최초 생성에 시간이 든다.
   모든 legacy 데이터 분포의 최초 업그레이드 비용은 측정하지 않았다. 기존 데이터 보존과
   재시작 후 동작은 검증했다.
6. Electron UI의 FPS·입력 지연, 실제 ComfyUI GPU 처리량·네트워크, 운영 DB의 최고 메모리,
   설치 패키지는 미측정이다. DB 서비스 구간의 실측 개선을 앱 전체의 개선율로 확장하지 않는다.
   전체 DB를 export하고 내구성 있게 저장하는 기존 I/O 자체는 여전히 존재한다.

## 정확성·회귀 검증

- 기준 상태: 77개 테스트 파일, **810개 통과**, 테스트 실패 없음. 첫 실행의 `spawn EPERM`은
  esbuild 자식 프로세스 권한 문제였고 `doctor`로 확인 후 권한을 조정해 정상 실행했다.
- 관련 검증: DB·큐 실패 경로·출력 journal·프로세스 강제 종료 등 **7개 파일, 163개 통과**.
- 추가한 5개 테스트는 다른 상태·다른 작업·실행 증거 보존, 정리 롤백·반복 호출·새 완료 반영,
  legacy DB 인덱스 생성과 재열기, async/sync 바이트 범위, 쓰기 전 DB 변경과 순차 저장을 검증한다.
- benchmark는 태스크·이미지 전체 컬럼 해시 동등성, 저장 파일 재열기와 `integrity_check`,
  갤러리 페이지 길이·총수를 확인했다.
- `npm run verify`: **78개 파일, 815개 테스트 통과**. lint·main/renderer/tests 타입 검사·
  전체 테스트·production bundle 빌드 모두 통과했다. 이번 실행은 59.73초, 종료 코드 0,
  `latest.json.status = passed`, `incomplete.json` 없음으로 확인했다.
- 기존 사용자 변경 29개 tracked 파일과 8개 새 파일은 시작 시점 diff·해시를 보관했다.
  이번 코드 수정은 DB 두 파일에 한정하고 CHANGELOG에 항목을 추가했다.

## 재현

저장소 루트에서 `.node-version`의 Node와 설치된 의존성을 사용한다. 실행기는 임시 userData를
만들고 결과를 `.reports/performance/<label>/`에 저장한다. 실제 userData나 ComfyUI를 사용하지
않으며, 끝나면 자신의 임시 DB만 제거한다. 다른 테스트·빌드·벤치마크와 동시에 실행하지 않는다.

```powershell
# 현재 코드: 최초 1회 별도 기록 + 워밍업 5회 + 측정 15회
node scripts/benchmark-database.mjs --label local-50000 --rows 50000 --samples 15 --warmup 5
node scripts/benchmark-database.mjs --label local-5000 --rows 5000 --samples 15 --warmup 5

# 이번 워크스페이스에 보관한 변경 전 소스와 같은 측정기로 비교
node scripts/benchmark-database.mjs --label local-before --source .reports/performance/before-source --rows 50000 --samples 15 --warmup 5

# 관련 회귀 및 전체 검증
npm test -- tests/main/services/database tests/main/services/batch/queue-manager.test.ts tests/main/services/batch/queue-faults.test.ts tests/main/services/batch/output-crash.test.ts tests/main/services/batch/output-journal.test.ts
npm run verify
```

`--scenario snapshot` 또는 `--scenario cleanup`으로 범위를 좁힐 수 있다. 비교용 `--source`는
다른 체크아웃의 루트도 받으며, 측정 코드와 패키지는 현재 체크아웃 것을 동일하게 사용한다.
이번 원본은 기존 미커밋 변경을 포함하므로 단순히 HEAD와 비교하면 같은 기준 상태가 아니다.
`.reports`의 소스 복사본·실행 번들은 로컬 재현용이며 Git에 포함하지 않는다.
